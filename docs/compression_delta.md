# Compression Delta: Codec Damage vs. Total Transport Cost

Generated by `R/07_compression_delta.R` on 2026-07-30 22:39. All three arms (compressed, codec-only uncompressed, full-fidelity uncompressed) are rebuilt from the same `data/raw/manifest.csv` on every run and evaluated with 5-fold grouped cross-validation, repeated 10 times with different fold assignments (50 fold-evaluations total) -- the SAME fold assignment is used across all three arms on a given repeat (verified, not just seeded identically). Every number below is the distribution across those fold-evaluations, not a single point estimate.

## What each arm actually is

- **Compressed**: the real webhook path -- WhatsApp's Opus/Ogg simulation 
  (16000Hz, 16kbps).
- **Codec-only (uncompressed)**: resampled to 16000Hz, no Opus round-trip. 
  Bandwidth held constant vs. the compressed arm -- isolates codec quantization 
  damage specifically, and says nothing about bandwidth loss.
- **Full-fidelity (uncompressed)**: resampled to a common 48000Hz, no Opus 
  round-trip. Isolates the TOTAL transport cost of using a WhatsApp voice note 
  (codec damage AND the bandwidth WhatsApp's 16kHz sample rate discards) against 
  a raw-upload alternative.

## The two deltas (uncompressed minus compressed, PAIRED per fold-iteration)

Paired means the same fold assignment (hence the same recording-level luck) is 
shared by all three arms on a given fold-iteration, so it cancels out of the 
difference between arms even where it doesn't cancel out of any single arm's raw 
accuracy above -- this is why the delta, not raw accuracy, is this report's 
headline comparison.

- **Codec-only delta: -1.1% (sd 4pp, range -8.8% to 6%, n=50)** -- the cost of the Opus codec specifically, bandwidth held constant.
- **Full-fidelity delta: 2.8% (sd 5pp, range -6.2% to 13%, n=50)** -- the TOTAL cost of using a WhatsApp voice note vs. a raw high-rate upload.
- **Bandwidth component (full-fidelity delta minus codec-only delta): 3.9% (sd 5.4pp, range -6.5% to 13.1%, n=50)** -- 
  the portion of the total cost attributable specifically to the 8kHz Nyquist 
  ceiling, on top of whatever the codec itself costs.

## Before/after: did expanding the corpus actually narrow this? (Prompt 8)

**Yes, substantially.** Prompt 7's 50-random-seed run on a 5-recordings-per-species 
corpus found per-arm accuracy ranging roughly 10-92% (SD ~26pp) and both deltas' 95% 
ranges spanning roughly +/-10 points. Prompt 8's corpus expansion + window cap + 
repeated grouped k-fold found per-arm accuracy SD around 4.4-5.4pp -- roughly a 5x 
tighter spread -- and delta ranges of roughly +/-5 to +/-9 points. This narrowing was 
itself a result: it demonstrated the earlier instability was substantially a sampling 
artifact (too few source recordings, no cap on how much one long recording could 
dominate a fold), not an inherent property of the classification task.

## Did adding temporal features shrink the delta further? (Prompt 9, Part 1)

**No -- report that plainly, as instructed, rather than only reporting the shrink that 
didn't happen.** The hypothesis was specific: amplitude-envelope/temporal structure 
should survive low-bitrate Opus better than fine spectral detail, so adding temporal 
features (syllable/pulse rate, inter-pulse intervals, envelope modulation spectrum, 
phrase-level structure) should make the classifier's accuracy LESS sensitive to 
compression, narrowing the delta. Measured result: codec-only delta went from +0.9% 
(Prompt 8, pre-temporal) to -1.1% (this run, post-temporal) -- both indistinguishable 
from zero, but the RANGE widened slightly (roughly +/-5 points to roughly +/-7.5 
points) rather than narrowing. Full-fidelity delta moved from +3.6% to +2.8% (also 
no meaningful shrink) and its own range widened too.

**This comparison is not perfectly isolated, and that caveat matters as much as the 
result.** Prompt 9 changed the window length (2.0s/1.0s hop -> 4.0s/2.0s hop, to give 
phrase-level features enough context -- see docs/methodology.md) AT THE SAME TIME as 
adding temporal features, so any change in compression sensitivity could reflect 
either change, not temporal features specifically. Given both deltas remain squarely 
inside noise before and after, the honest conclusion is: this run found no evidence 
that adding temporal features narrows the compression delta, and modestly more 
evidence (still not conclusive) that the two arms differ, in whichever direction the 
next re-split happens to draw. If temporal robustness to compression is worth testing 
cleanly, it needs a run that changes ONLY the feature set, holding window length fixed.

## Interpretation

**Both deltas' 95% ranges still include zero, so neither is distinguishable from
 zero at conventional confidence.** Codec-only delta -1.1% (range -8.8% to +6.0%):
 squarely indistinguishable from zero -- the Opus codec itself, isolated from any
 bandwidth change, cannot be shown to cost this classifier anything measurable on real
 Orthoptera/Cicadidae audio, temporal features included. Full-fidelity delta +2.8%
 (range -6.2% to +13.0%) is again the more ambiguous of the two: point estimate
 positive and consistent with `docs/codec_findings.md`'s signal-level finding that
 content above 8kHz is destroyed outright, but the range still comfortably straddles
 zero, more so than the pre-temporal-feature run. Bandwidth component +3.9% (range
 -6.5% to +13.1%): same story, derived from the full-fidelity delta.

**What this does and doesn't say:** consistent with, and not contradicting, the
 codec experiment's finding that real Orthoptera stridulation survives compression
 well -- but this corpus cannot yet put a tighter than roughly +/-7 to +/-10 point
 precision on that claim at the classifier level, and adding temporal features did not
 change that. Does not extend to chewing-sound classes (excluded from this comparison,
 see docs/methodology.md) or to any untested condition (field noise, distance, phone
 microphone variability).
